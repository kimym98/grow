# PRD v2: Grow 데스크탑 앱 - 개선 및 확장

## 1. 개요

### 1.1 배경
`PRD_v1.md`에 정의된 0~6단계 로드맵 중 1~5단계(공고 크롤링, 캘린더/일정관리, IT뉴스 크롤링, 자소서/포트폴리오 PDF 첨삭, CS 면접 퀴즈)에 해당하는 1차 개발이 완료된 상태다. 이번 PRD v2는 1차 개발 완료 후 진행된 코드 리뷰(`docs/code-review.md`) 결과 반영과, 실사용 과정에서 확인된 UI 미흡점 개선, 그리고 서비스 완성도를 높이기 위한 신규 기능 추가를 다룬다.

### 1.2 목표
- **CI 파이프라인 정상화 및 Sentry 모니터링 실연동** (최우선 — 병합 파이프라인이 막혀 있어 다른 모든 과제의 선행 조건)
- 코드 리뷰에서 지적된 보안·아키텍처·성능 이슈를 심각도에 따라 단계적으로 해소
- 크롤링 소스 확장과 LLM 기반 기업 분석으로 채용 정보의 활용 가치 향상
- 서류 첨삭 기능의 정확도와 결과 화면 UX 개선
- CS 퀴즈를 사용자 참여형(직접 등록·공유) 구조로 확장

### 1.3 대상 사용자
- PRD v1과 동일 (IT 직군 취업 준비생, 공고 탐색·서류 작성·CS 지식 점검을 반복 수행하는 사용자)
- 신규 기능(기업 분석, CS 문제 공유) 추가로 커뮤니티성 문제뱅크에 기여하는 사용자층 포함

### 1.4 비범위 (Out of Scope)
- 외부 기업 리뷰/재무 데이터 연동 (기업 분석은 자체 수집 채용공고 데이터 기반으로 한정)
- 모바일 확장 (PRD v1 6단계, 별도 진행)
- 실시간 채팅/커뮤니티 전체 기능 (CS 문제 공유는 문제뱅크 단위로 한정, 채팅/댓글 등은 제외)
- 캘린더/스크롤바 UI 개선은 스타일링에 한정, 기능 로직 변경 없음

## 2. 핵심 개선·신규 과제

### 2.1 스크롤바 UI 개선
- **현황**: 기본 브라우저/OS 스크롤바가 그대로 노출되어 앱 전반의 디자인 톤과 이질감
- **개선 방향**: 앱 전역(사이드바, 리스트 뷰 등 스크롤 영역)에 커스텀 스크롤바 스타일 적용 (다크모드 대응 포함)
- **범위**: 시각적 스타일링만 해당, 스크롤 동작 로직 변경 없음

### 2.2 캘린더 UI 개선
- **현황**: 2단계에서 구현된 캘린더(월/주 뷰, 일정 요약)의 레이아웃/색상 등 시각적 완성도가 낮음
- **개선 방향**: 카테고리별(서류마감/면접/스터디) 색상 체계 정비, 간격/타이포그래피 정리, 오늘 일정 요약 영역 레이아웃 개선
- **범위**: 시각적 스타일링만 해당, 일정 등록/알림 등 기능 로직 변경 없음

### 2.3 LLM API 키가 렌더러 프로세스에서 직접 외부로 전송됨 (우선순위: 상)
- **문제**: `apps/desktop/lib/llm-keys.ts`의 `testLlmKey` 함수가 사용자가 입력한 Anthropic/Gemini API 키를 클라이언트(Electron 렌더러)에서 직접 `fetch()`로 외부 LLM API에 호출한다. Anthropic 호출 시 `anthropic-dangerous-direct-browser-access: true` 헤더까지 명시적으로 설정하고, Gemini 호출은 `?key=${apiKey}` 형태로 URL 쿼리 스트링에 키를 그대로 담는다.
- **영향**: 실제 채점(`grade-short-answer`)·문서 리뷰(`review-document`) 경로는 Edge Function에서 서버 측 복호화 키로 안전하게 처리되는데, 키 검증(`testLlmKey`)만 예외적으로 클라이언트에서 실행되어 경로 간 일관성이 깨진다. `contextIsolation`이 켜져 있어도 렌더러는 웹 콘텐츠이므로 XSS, 의존성 취약점, 개발자도구를 통한 네트워크 탭 노출 등으로 유효한 API 키가 유출될 위험이 있다. URL 쿼리 스트링에 담긴 키는 프록시/로그에 평문으로 남을 가능성도 있다.
- **해결방안**: 키 검증도 Edge Function을 경유하도록 통일한다. `validate-llm-key`라는 경량 Edge Function을 두고, 렌더러는 이 함수를 호출해 서버가 대신 외부 API에 최소 비용(1토큰) 요청을 보내 유효성만 반환받는 방식으로 전환한다.
  - `validate-llm-key`는 기존 함수 신뢰 경계 컨벤션에 맞춰 `auth: ["user"]`로 사용자 JWT 인증을 요구한다.
  - 서버는 전달받은 키를 **로깅/저장하지 않고** 유효성 결과(boolean + 메시지)만 응답하며, 응답 본문에 키를 다시 포함하지 않는다.
  - 남용 방지를 위해 사용자 단위 레이트리밋(예: 분당 N회)을 둔다.
  - **잔여 리스크**: 이 구조로 전환해도 키는 여전히 클라이언트→서버로 1회 전송된다(전송 자체가 사라지는 것은 아님). 렌더러가 직접 외부 LLM API를 호출하지 않게 되어 XSS/개발자도구를 통한 유출 경로와 URL 쿼리 노출을 제거하는 데 의의가 있다는 점을 인지하고, 전송 구간은 HTTPS로만 이뤄지는지 확인한다.
  - 부득이 클라이언트 직접 호출을 유지해야 한다면 최소한 Gemini 키는 쿼리 스트링 대신 헤더로 전달하고, CSP(T-L3)로 이 호출을 허용된 origin으로 제한한다. **이 폴백은 T-L3(CSP 미설정)가 선행 적용되어야 유효하므로, T-L3를 1단계로 앞당겨 함께 처리한다.**

### 2.4 하드코딩된 테스트 계정 자격증명의 프로덕션 노출 방지 보완 (우선순위: 상)
- **문제**: `apps/desktop/lib/auth-test.ts` 7-8행에 `TEST_ACCOUNT_EMAIL`/`TEST_ACCOUNT_PASSWORD`가 평문으로 하드코딩되어 있다(`qa-tester@example.com` 등 예시 도메인 사용 중이라 현재 실계정 탈취 위험은 낮으나, 구조적으로는 동일한 문제). 주석에는 "프로덕션 빌드에서는 렌더링되지 않는다"고 되어 있지만, 파일 자체에는 `NODE_ENV`에 따른 조건부 export나 트리쉐이킹을 보장하는 장치가 보이지 않는다.
- **영향**: Next.js 정적 export 특성상 이 상수들이 조건 없이 클라이언트 번들에 포함되면, 배포된 앱 바이너리(`asar` 압축 해제, 문자열 추출)에서 테스트 계정 자격증명이 그대로 발견될 수 있다. 현재 산출물(`apps/desktop/out/`) 문자열 검색 결과 해당 상수는 검출되지 않았으나, 빌드 시점이 최신인지 보장되지 않으므로 프로덕션 빌드 직후 재확인이 필요하다.
- **방침**: 테스트 계정 자체는 로그인 자동화(2.16 Playwright E2E 하네스)에서 계속 필요하므로 **제거하지 않고, 프로덕션 빌드에 노출되지 않도록 구조적으로 격리**하는 방향으로 보완한다.
- **해결방안**:
  1. 빌드된 프로덕션 산출물(`dist`/`out`)을 매 릴리스 전 `grep -r "TEST_ACCOUNT" out/`로 문자열 검색해 번들 포함 여부를 CI에서 자동 확인한다(포함 시 빌드 실패 처리).
  2. 자격증명 값 자체를 소스코드에서 제거하고 **환경변수**(`E2E_TEST_ACCOUNT_EMAIL`/`E2E_TEST_ACCOUNT_PASSWORD`)로 이전한다. 프로덕션 빌드 파이프라인에는 이 환경변수를 주입하지 않아 값 자체가 번들에 들어갈 원천을 차단한다.
  3. `auth-test.ts`를 dev/CI 전용 진입점으로 분리(예: `lib/auth-test.dev.ts` + 별도 `tsconfig`/번들 제외 설정)하여 프로덕션 빌드 대상에서 파일 자체가 제외되도록 한다.
  4. **Supabase 계정 측 조치**: 코드에서 값을 지워도 Supabase Auth에는 해당 계정이 남아있으므로, (a) 이 계정에 최소 권한(RLS상 일반 사용자와 동일, 관리자 권한 없음)만 부여되어 있는지 확인하고, (b) 비밀번호를 주기적으로 로테이션하며, (c) 실제 사용자 데이터와 분리된 전용 테스트 프로젝트/스키마 사용을 검토한다.
  5. 위 조치 완료 후에도 매 릴리스 전 1번 문자열 검색을 CI 게이트로 유지해 재발을 방지한다.

### 2.5 LLM 호출/프롬프트 로직 3중 복제 (우선순위: 중)
- **문제**: `fetchWithRetry`, JSON 파싱, 프롬프트 템플릿 로직이 `packages/shared/src/lib/llm/*`, `supabase/functions/grade-short-answer/llm.ts`, `supabase/functions/review-document/llm.ts` 세 곳에 사실상 동일하게 복제되어 있다. `review-document/llm.ts`의 프롬프트 문자열은 `packages/shared`의 `buildDocumentReviewPrompt`와 완전히 동일하다. `electron/notification-trigger.ts`에도 주석으로 "shared와 동일 로직의 복제본, 함께 갱신 필요"라고 명시된 유사 패턴이 있다.
- **영향**: 한쪽 프롬프트나 재시도 정책만 수정하고 다른 쪽을 놓치는 드리프트가 발생하기 쉽다. 현재는 "Deno ESM이 확장자 없는 상대 임포트를 지원하지 않는다"는 이유로 복제를 택했지만, 이는 진입점 설계로 해결 가능한 문제다.
- **해결방안**: `packages/shared`에 Deno 호환 전용 배럴 파일(예: `src/lib/llm/deno-entry.ts`, 확장자 포함 상대 경로만 사용)을 만들어 Edge Function에서 `import { fetchWithRetry } from "../../../packages/shared/src/lib/llm/deno-entry.ts"` 형태로 재사용하도록 리팩토링한다. 최소한 프롬프트 템플릿만이라도 단일 소스로 통합하는 것을 우선순위로 둔다. **2.11(이력서/포트폴리오 첨삭 개선)에 앞서 선행 완료해야, 개선된 프롬프트가 즉시 단일 소스에 반영되는 효과를 볼 수 있다.**

### 2.6 LLM 호출 타임아웃 누적이 Edge Function 실행 한도를 초과할 위험 (우선순위: 중)
- **문제**: `fetch-with-retry.ts` 및 두 Edge Function 복제본 모두 60초 타임아웃 × 최대 3회 재시도 정책을 사용한다. 5xx/429 응답이 반복되면 최악의 경우 약 3분간 대기하게 된다.
- **영향**: Supabase Edge Function의 실행 시간 제한을 초과해 함수가 강제 종료될 수 있다. 특히 `review-document`는 PDF 파싱까지 포함되어 있어, 함수가 타임아웃으로 kill되면 `catch` 블록의 `status = "failed"` 업데이트조차 실행되지 못하고 리뷰 레코드가 `processing` 상태로 영구히 멈춰있을 수 있다.
- **해결방안**: 전체 재시도 예산에 상한을 두는 시간 기반 타임아웃(예: 전체 90초 초과 시 즉시 실패 처리)을 도입하고, DB에 `processing` 상태로 일정 시간 이상 머무른 레코드를 감지해 `failed`로 전환하는 워치독(스케줄 함수 또는 클라이언트 폴링 시 타임아웃 판정)을 추가한다.

### 2.7 웹 스크레이핑의 견고성 부족과 rate limiting 부재 (우선순위: 상, 2단계로 선행)
- **문제**: `collect-job-postings/sources/jobkorea.ts`가 정규식으로 HTML을 직접 파싱한다. 대상 사이트의 DOM 구조가 조금만 바뀌어도 파싱 전체가 깨질 수 있는 구조다. 또한 `collect-job-postings`/`collect-tech-news` 어디에도 요청 간 딜레이나 백오프 로직이 없어, 주기적 cron 실행 시 짧은 시간에 반복 요청이 나가면 대상 사이트로부터 IP 차단을 당할 위험이 있다.
- **영향**: 파싱 실패가 잦아지면 데이터 수집 기능 자체의 신뢰성이 떨어지고, 과도한 요청은 대상 사이트에 부담을 주며 서비스 이용약관 위반으로 이어질 수 있다. **2.9로 소스가 3개로 늘어나면 전체 요청량이 늘어나 이 위험이 커지므로, 신규 소스 추가보다 먼저 처리한다.**
- **해결방안 (2단계 — 딜레이/백오프/모니터링, 소스 확장과 무관하게 선행)**:
  - `collect-job-postings`/`collect-tech-news` 소스별 요청 사이에 최소 간격(예: 1~2초)을 두는 딜레이 로직 추가
  - 파싱 실패율이 일정 임계치(예: 소스별 실패율 30% 초과)를 넘으면 알림을 보내는 모니터링 추가 — 수용 기준: 임계치·측정 주기를 구현 시 확정해 수집 로그 테이블 기준 대시보드/알림으로 연결
- **해결방안 (3단계 — DOM 파서 교체, 2.9 신규 소스 작업과 함께)**: 가능하면 정규식 파싱을 공식 API나 DOM 파서(`deno-dom` 등 Deno 호환 라이브러리)로 교체해 구조 변경에 대한 내성을 높인다. **2.9(캐치·자소설닷컴 추가) 작업과 함께 적용**하여 신규 소스도 동일한 견고성 기준으로 구현한다.

### 2.8 자동 업데이트 코드 서명 검증 비활성화 (우선순위: 중, 신청은 1단계 병행)
- **문제**: `apps/desktop/package.json`에서 `verifyUpdateCodeSignature: false`로 설정되어 있다. `docs/guides/electron-release-guide.md`에 "코드 서명 인증서가 없어 임시로 비활성화했다"고 문서화는 되어 있다.
- **영향**: GitHub Releases 배포 채널이 탈취되거나 전송 계층이 손상될 경우, 서명 검증 없이 임의의 실행 파일이 사용자 PC에 자동 설치될 수 있는 구조적 위험이 있다.
- **해결방안**: 코드 서명 인증서(EV 인증서 또는 최소한 표준 인증서) 발급은 리드타임이 수 주 단위이므로 **1단계(보안 이슈 해소)와 병행해 발급 신청을 미리 시작**하고, 실제 `verifyUpdateCodeSignature: true` 전환·적용은 인증서 확보 시점(7단계)에 맞춰 진행한다. 단기적으로는 **다음 릴리스부터 즉시** 릴리스 아티팩트의 체크섬(SHA256)을 릴리스 노트에 함께 게시해 최소한의 무결성 확인 수단을 제공한다(별도 선행 조건 없음).

### 2.10 기업 분석 기능 (신규 기능, 우선순위: 중)
- 자체 수집한 `job_postings` 데이터를 기업 단위로 집계하여 LLM에 전달, 해당 기업의 채용 특징/기술 스택 트렌드/직무 분포 등을 요약·분석
- 외부 리뷰·재무 데이터 연동 없음 — 순수하게 자체 수집 채용공고 데이터 기반 분석으로 범위 한정
- 기업 상세 페이지(또는 공고 상세에서 진입)에서 "기업 분석 보기" 액션 제공, 최초 요청 시 LLM 호출 후 결과 캐시, 이후 재방문 시 캐시 결과 표시(수동 새로고침으로 재분석 가능)
- LLM 호출은 2.5 정리 방향에 맞춰 Edge Function(`analyze-company`)에서 처리, `packages/shared`의 공통 LLM 호출 로직 재사용
- **분석 결과는 사용자별로 소유**한다. 분석 호출이 사용자 개인 LLM 키로 이루어지므로, 기존 `llm-cache.ts`가 채택한 `user_id` 기반 RLS 크로스토크 방지 원칙을 동일하게 적용해 A의 키로 만든 결과를 B가 비용 부담 없이 소비하는 문제를 막는다
- **기업명 정규화**: `job_postings.company` 값은 "㈜", "주식회사", 국문/영문 표기가 뒤섞여 있을 수 있으므로, 분석 집계 전에 정규화 함수(또는 별도 `company_id` 매핑 테이블)를 거쳐 동일 기업의 공고가 다른 키로 파편화되지 않도록 한다
- **캐시 무효화**: 2.12(해시 기반 캐시 자동 무효화)와 동일한 원칙을 적용해, 캐시 키에 프롬프트 해시뿐 아니라 **집계 대상 공고 집합의 해시**(예: 대상 `job_postings.id` 목록 해시)를 포함시킨다. "기반 공고 기간"만으로는 동일 기간 내 신규 공고가 추가돼도 캐시가 무효화되지 않는 문제가 있다

**데이터 모델**: `company_analyses` (`user_id`, 기업명, 정규화된 `company_id`, 분석 요약, 기술 스택 트렌드, 채용 공고 수, 기반 공고 기간, 생성일시, 캐시 키 해시)

### 2.11 이력서/포트폴리오 첨삭 기능 개선 (신규 기능, 우선순위: 중)
- **(a) 첨삭 품질/정확도 향상**: `review-document` 프롬프트 템플릿 개선(문항별/포트폴리오 유형별 세분화, 예시 기반 few-shot 보강). 2.5(3중 복제 통합)가 이 작업에 앞서 선행 완료되어 있어야, 개선된 프롬프트가 `packages/shared` 단일 소스에서 즉시 모든 진입점에 반영된다
- **(b) 첨삭 결과 화면 UI/UX 개선**: 기존 diff/코멘트 형태 렌더링을 원문-첨삭본 비교뷰(좌우 또는 인라인 하이라이트)로 개선, 코멘트별 심각도/카테고리 하이라이트 색상 구분, 첨삭 이력 버전 간 비교 UI 추가
  - **구현 방식 주의**: 현재 파이프라인은 PDF→텍스트 추출 방식이라 원본 PDF의 좌표 정보가 소실된다. 따라서 LLM이 좌표를 직접 반환하도록 요구하지 않고, **LLM에는 하이라이트할 인용 문구(quote)를 반환시킨 뒤 서버가 추출된 텍스트에서 해당 문자열을 검색해 위치(offset)를 계산**하는 방식으로 구현한다. 문자열 매칭에 실패하는 경우(LLM이 원문을 살짝 바꿔 인용하는 등)를 대비해 **하이라이트 없이 코멘트만 표시하는 폴백**을 명시적으로 둔다
  - 기존 `review-document`에 이미 존재하는 첨삭 이력 `versions` 컬럼과의 관계를 먼저 정리한 뒤(버전별로 하이라이트 메타데이터를 함께 저장할지, 최신 버전에만 적용할지) "이력 버전 간 비교 UI"를 설계한다
- 2.12(캐시 무효화 자동화)가 이 작업에 앞서 선행 완료되어 있어야, 프롬프트 개선 시 캐시가 자동 무효화되어 개선 효과를 바로 확인할 수 있다

**데이터 모델 변경**: `document_reviews`에 하이라이트 메타데이터 필드 추가 (인용 문구, 텍스트 내 offset, 카테고리, 심각도, 매칭 성공 여부)

### 2.12 캐시 무효화가 수동 버전 관리에 의존 (우선순위: 중)
- **문제**: `grade-short-answer/index.ts`, `review-document/index.ts`의 `PROMPT_VERSION` 상수를 프롬프트 변경 시 사람이 수동으로 올려야 캐시가 무효화된다.
- **영향**: 프롬프트를 수정하고 버전을 올리는 것을 잊으면, 이전 프롬프트 기준으로 캐시된 결과가 계속 재사용되어 품질 저하를 인지하기 어렵다.
- **해결방안**: 캐시 키 생성 시 프롬프트 템플릿 문자열 자체의 해시를 포함시켜 자동으로 무효화되도록 바꾼다. **2.11(이력서/포트폴리오 첨삭 개선)에 앞서 선행 완료**해두면, 이후 프롬프트를 변경할 때마다 캐시가 자동으로 갱신되어 개선 효과를 바로 확인할 수 있다. 동일한 해시 기반 캐시 키 원칙은 2.10(기업 분석)의 캐시 무효화에도 함께 적용한다.

### 2.13 리스트 행 컴포넌트의 메모이제이션 누락 (우선순위: 중)
- **문제**: `jobs-page-client.tsx`, `news-feed.tsx`에서 `react-window`로 가상화는 되어 있지만 각 행 컴포넌트(`JobRow`, `NewsRow`)에 `React.memo`가 적용되어 있지 않고, `itemData`로 넘기는 `rowProps` 객체와 `handleSelectJob` 콜백이 매 렌더마다 새로 생성된다(`useCallback`/`useMemo` 미사용).
- **영향**: 가상화로 DOM 노드 수는 줄였지만, 부모 리렌더 시마다 화면에 보이는 모든 행이 다시 렌더링되어 가상화의 이점이 상쇄된다.
- **해결방안**: 행 컴포넌트를 `React.memo`로 감싸고, `rowProps`와 이벤트 핸들러를 `useMemo`/`useCallback`으로 안정화한다.
```tsx
const JobRow = React.memo(function JobRow({ index, style, data }: RowProps) {
  // ...
});

const handleSelectJob = useCallback((id: string) => setSelectedJobId(id), []);
const rowProps = useMemo(
  () => ({ jobs: filteredJobs, selectedJobId, onSelect: handleSelectJob }),
  [filteredJobs, selectedJobId, handleSelectJob]
);
```

### 2.14 CS 문제 입력 및 공유 기능 (신규 기능, 우선순위: 중)
- 기존 자체 큐레이션 문제뱅크(PRD v1 5단계)에 사용자가 직접 문제를 등록하는 기능 추가 (카테고리, 문제, 정답/해설 입력)
- 등록한 문제를 공개로 전환해 다른 사용자와 공유하거나, 커뮤니티 문제뱅크로 편입 가능하도록 확장
- 문제 목록 화면에서 "내 문제" / "공개 문제뱅크" 탭 구분

**데이터 모델 변경**: `cs_questions`에 `author_id`(작성자, `auth.users` 참조), `is_public`(공개 여부), `source_type`(`curated` | `user_generated`) 필드 추가

**RLS 정책 방향**:
- SELECT: `is_public = true`이거나 `author_id = auth.uid()`인 행만 조회 가능
- INSERT: 인증된 사용자만 자신을 `author_id`로 하는 행 생성 가능. `WITH CHECK`에 `author_id = auth.uid() AND source_type = 'user_generated'`를 강제해, 사용자가 자신의 문제를 `curated`로 위장 등록하는 것을 차단한다
- UPDATE: `USING (author_id = auth.uid())`뿐 아니라 `WITH CHECK (author_id = auth.uid())`도 함께 걸어 수정 중 `author_id` 자체를 바꿔치기하는 것을 차단한다 (공개 전환된 문제라도 원 작성자만 수정/삭제)
- DELETE: `author_id = auth.uid()`인 본인 문제만 가능. 단, 공개 전환되어 다른 사용자의 `quiz_sessions`/`user_answers`에서 이미 참조 중인 문제가 삭제되면 이력이 깨지므로, 하드 삭제 대신 **soft delete**(`is_deleted` 플래그) 또는 `ON DELETE` 시 참조 레코드를 보존하는 정책을 적용한다
- 큐레이션 문제(`source_type = curated`)는 일반 사용자 UPDATE/DELETE 대상에서 제외 (관리자 전용 별도 정책 또는 서비스 롤 경유)
- **실시간 구독 영향 확인**: `lib/realtime-sync.ts`는 "SELECT RLS가 무조건 허용되는 공개 데이터"라는 전제로 공개 채널을 구독하는 구조다(코드 주석에 명시). `cs_questions`가 사용자별 RLS(비공개 문제 포함)를 갖게 되면 이 전제가 깨질 수 있으므로, 이 테이블이 기존 실시간 구독 대상에 포함되는지 먼저 확인하고, 포함된다면 공개(`is_public = true`) 행만 별도 채널로 분리해 구독한다

### 2.16 Playwright E2E 검증 하네스 구축 (신규 과제, 우선순위: 중)
- **현황**: 저장소에 Playwright 의존성이 전혀 없다(`package.json` 기준 `vitest run`만 존재). 즉 5장의 E2E 검증 계획은 검증 체크리스트가 아니라 **하네스를 처음부터 구축하는 별도 개발 과제**이므로 로드맵에 독립 단계로 반영한다.
- **Electron 구동 방식**: Playwright의 `_electron.launch()`로 **패키징된 실행 파일**(`electron-builder` 산출물)을 구동 대상으로 선택한다. dev 서버 대상보다 실 사용 환경에 가깝고, T-L8(패키징 스모크 테스트)의 목적과 정확히 겹치므로 별도 스모크 테스트를 만들지 않고 이 하네스로 통합한다.
- **로그인 자동화**: 구글 OAuth는 `shell.openExternal`로 외부 브라우저를 여는 구조라 Playwright로 자동화할 수 없다. 자동화 가능한 유일한 경로는 2.4에서 환경변수로 이전한 테스트 계정(`E2E_TEST_ACCOUNT_EMAIL`/`PASSWORD`)이며, CI 환경에서만 이 값을 시크릿으로 주입해 로그인한다.
- **검증 가능/불가능 항목 분리**:
  - 가능: 채용공고 목록/필터/상세 조회, 캘린더 UI 렌더링(스타일 개선 후 스크린샷 비교), PDF 업로드→첨삭 비교뷰 렌더링, CS 문제 등록→공개 전환 UI 플로우
  - 불가능(대체 방식 필요): OS 레벨 `Notification`은 Playwright로 관측 불가 — 메인 프로세스의 알림 트리거 함수 호출/IPC 로그를 훅으로 어서션하는 방식으로 대체. RLS 정책(2.14) 검증은 E2E보다 anon/authed `supabase-js` 클라이언트 단위 테스트(또는 pgTAP)가 더 빠르고 결정적이므로 E2E는 UI 플로우만 담당
- **스크린샷 비교 기준선**: 9단계(UI 스타일링 개선) 적용 **이후** 시점에 기준 스냅샷을 확정한다(개선 전에 찍으면 9단계 완료 시 전량 실패). 허용 오차·폰트 렌더링 차이 정책을 구현 시 확정
- **외부 사이트 의존 최소화**: 2.9 신규 크롤링 소스 E2E는 실제 외부 사이트 응답에 의존하면 flaky해지므로 시드 픽스처(수집 로그 테이블에 미리 적재한 샘플 데이터) 기반으로 UI 노출만 검증하고, 실제 크롤링 성공 여부는 2.7의 모니터링/알림으로 별도 확인
- **CI 실행 환경**: Electron GUI는 헤드리스가 아니므로 Windows 러너 또는 Linux+xvfb 중 CI 환경에 맞춰 결정하고, 회귀 방지를 위해 주요 플로우를 CI 스모크 테스트로 등록

### 2.17 CI 린트 실패 긴급 수정 (신규 발견, 우선순위: 최상 — 즉시 조치, 0단계)
- **문제**: 현재 GitHub Actions CI(`ci.yml`)의 Lint 단계가 7개 에러로 실패해 **병합 파이프라인 자체가 막혀 있다.** 실제 로그 기준 원인은 두 갈래다.
  1. **`electron/main.ts:47`, `electron/preload.ts:8`**: `@typescript-eslint/no-require-imports` 위반. 이는 code-review.md에서 지적된 Sentry 정적 import 크래시(`Cannot find module '@sentry/browser-utils'`)를 막기 위해 `docs/troubleshooting/electron-packaging-troubleshooting.md`에 기록된 **임시방편**으로 `require()` 지연 로드를 도입한 결과다. 정적 import로 되돌리면 원래의 패키징 크래시가 재발하므로, "SENTRY_DSN이 있을 때만 로드"라는 지연 로드 자체는 유지하되 lint 규칙을 준수하는 방식으로 교체해야 한다.
  2. **`theme-toggle.tsx`, `news-card.tsx`, `carousel.tsx`**: `react-hooks/set-state-in-effect` — effect 내부에서 setState를 동기 호출해 캐스케이딩 렌더를 유발(React Compiler 도입에 따른 신규 규칙). **`today-news-carousel.tsx`**: `react-hooks/purity`(렌더 중 `Math.random()` 호출로 순수성 위반) + `react-hooks/use-memo`(의존성 배열에 인라인 표현식 사용). 이 5건은 Sentry와 무관한 별개의 React 규칙 위반이다.
- **영향**: 이 상태에서는 어떤 PR도 CI를 통과할 수 없어, 이번 PRD의 모든 후속 과제(2.1~2.16)가 착수는 가능해도 병합·배포는 불가능하다. 문서상 모든 단계보다 먼저 처리해야 한다.
- **해결방안**:
  1. `main.ts`/`preload.ts`: 함수 최상단 `require()` 대신 함수 내부 `await import(...)` 동적 import로 전환한다. ESM 동적 import는 `no-require-imports` 규칙 위반이 아니며, "DSN 없으면 모듈 자체를 로드하지 않는다"는 지연 로드 목적도 그대로 유지된다. 변경 후 반드시 `npm run build` → `electron-builder`로 실제 패키징 후 설치·실행까지 재검증한다(과거 트러블슈팅 문서의 검증 절차와 동일하게, dev 서버에서는 재현되지 않는 유형의 문제였음을 감안).
  2. `theme-toggle.tsx`/`news-card.tsx`/`carousel.tsx`: "마운트 후 1회 상태 반영" 패턴을 초기값 계산 또는 `useSyncExternalStore` 등으로 재구성해 effect 내 동기 setState를 제거한다.
  3. `today-news-carousel.tsx`: `Math.random()` 기반 랜덤 배경색 배정을 `news.id` 기반 결정론적 해시 등 순수 함수로 교체하고, `useMemo` 의존성 배열을 단순 표현식으로 정리한다.
  4. 수정 후 `npm run lint`를 CI와 동일 조건(Node 20)으로 로컬 재현해 0 에러를 확인한 뒤 병합한다.
- **로드맵 배치**: 문서 전체에서 가장 먼저 처리하는 0단계로 배치한다(3장 마이그레이션 파일화보다도 선행 — 마이그레이션 작업 PR 역시 이 CI를 통과해야 하기 때문).

### 2.18 Sentry DSN 실연동 및 대시보드 구축 (신규 발견, 우선순위: 상)
- **문제**: Sentry 통합 코드(`electron/main.ts`, `electron/preload.ts`, `lib/sentry.ts`)는 이미 존재하지만, `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN`이 로컬 `.env.example`, GitHub Secrets 어디에도 실제 값으로 설정되어 있지 않다(`release.yml` 주석에 "아직 이 프로젝트에 발급된 값이 없다"고 명시됨). 즉 현재는 배선만 되어 있고 실제로는 완전히 꺼져 있는 모니터링이다.
- **영향**: 배포된 앱에서 크래시나 에러가 발생해도 어디에도 리포팅되지 않아, 사용자가 직접 알리지 않는 한 개발자가 문제를 인지할 방법이 없다. 2.17에서 다룬 임시방편(lazy require) 같은, "패키징 환경에서만 재현되는" 유형의 문제가 앞으로도 재발할 수 있는데, 실 모니터링 없이는 발견이 늦어질 수밖에 없다.
- **해결방안**:
  1. Sentry 프로젝트를 신규 생성(또는 기존 조직에 Electron 프로젝트 추가)해 DSN을 발급받는다.
  2. `SENTRY_DSN`(main 프로세스용), `NEXT_PUBLIC_SENTRY_DSN`(렌더러용)을 GitHub Secrets에 등록하고, `release.yml`의 배포 빌드 단계에서 이미 준비된 `env:` 자리에 연결한다.
  3. 로컬 개발(`next dev`)에서는 DSN을 비워둬 기존처럼 no-op으로 유지하고, **릴리스 빌드에서만** 활성화되도록 해 개발 중 노이즈를 방지한다.
  4. 연동 후 임시 `throw`로 실제 크래시를 인위 발생시켜 Sentry 대시보드에 에러가 정상 수집되는지 검증한다.
  5. 소스맵 업로드를 설정해 대시보드에서 스택 트레이스가 압축된 코드가 아닌 원본 코드 위치로 매핑되는지 확인한다.

## 5. 검증 방법
- 각 단계마다 `npm run dev`로 Electron 앱 실행 후 end-to-end 기능 확인
- Supabase Edge Function은 `supabase functions serve`로 로컬 테스트 후 배포
- 0단계(CI 린트 긴급 수정, 2.17): `npm run lint`를 CI와 동일한 Node 20 환경에서 0 에러로 통과하는지 확인, `main.ts`/`preload.ts` 동적 import 전환 후 `npm run build` → `electron-builder`로 실제 패키징·설치·실행까지 재검증(SENTRY_DSN 미설정 시 여전히 크래시 없이 기동하는지 확인)
- 0-1단계(마이그레이션 파일화): `supabase db diff`로 기존 원격 스키마와 신규 마이그레이션 파일 적용 결과가 일치하는지 확인
- Sentry 실연동(2.18): DSN 등록 후 임시 `throw`로 크래시를 인위 발생시켜 Sentry 대시보드에 실제로 수집되는지 확인, 소스맵 업로드 후 스택 트레이스가 원본 코드 위치로 정상 매핑되는지 확인, 로컬 dev 환경에서는 여전히 no-op으로 남아있는지 확인
- 보안 항목(2.3, T-L3, 2.4): 프로덕션 빌드 산출물(`out`/`dist`)을 CI에서 `grep -r "TEST_ACCOUNT" out/`로 자동 검색해 실패 시 빌드 차단. `validate-llm-key` 응답에 원본 키가 포함되지 않는지, 서버 로그에 키가 남지 않는지 확인
- 스크레이핑 견고성(2.7): 소스별 딜레이 적용 후 짧은 시간 반복 호출 시 대상 사이트로부터 차단(429/403) 없이 정상 수집되는지 확인, 파싱 실패율 임계치 초과 시 알림이 실제로 발송되는지 확인
- LLM 로직 통합(2.5): 통합 후 `grade-short-answer`, `review-document` 각각 실제 호출로 응답 동일성 확인
- 사전 스파이크(3단계 착수 조건): 캐치 `/api/v1.0/recruit/*` 엔드포인트 실존 여부·응답 스키마, 자소설닷컴 공고 상세 페이지의 서버사이드 렌더링 여부, 양측 이용약관상 크롤링 제한 여부를 `docs/research/`에 기록 후 착수 여부 최종 판단
- 크롤링 확장(2.9): 스파이크 결과에 따라 확정된 방식(캐치는 API 우선, 자소설닷컴은 HTML/사이트맵)으로 `supabase functions serve` 로컬 실행 후 수집 로그 테이블에 소스별 성공/실패가 정상 기록되는지, 중복 게재 공고가 집계 시 대표 1건으로 처리되는지 확인
- 기업 분석(2.10): 실제 수집된 공고 데이터를 기반으로 `analyze-company` 호출 후 결과 캐시/재조회 동작 확인, 서로 다른 사용자 계정으로 호출 시 캐시가 공유되지 않는지(RLS) 확인, 신규 공고 추가 후 캐시가 자동 무효화되는지 확인
- 첨삭 개선(2.11): 실제 샘플 PDF로 업로드 → 개선된 프롬프트 첨삭 → 비교뷰 UI까지 수동 테스트, 인용 문구 매칭 실패 시 폴백(하이라이트 없이 코멘트만 표시)이 정상 동작하는지 확인
- CS 문제 공유(2.14): 서로 다른 두 계정으로 비공개/공개 문제 조회 권한이 RLS 정책대로 분리되는지 확인(anon/authed `supabase-js` 클라이언트 단위 테스트로 우선 검증), `curated` 위장 등록 시도가 차단되는지 확인, 공개 문제가 다른 사용자 세션에서 참조된 상태에서 삭제 시 soft delete로 처리되는지 확인
- **Playwright E2E 검증(2.16)**: 하네스 구축 후 주요 사용자 플로우를 자동 검증
  - 테스트 계정(환경변수 주입) 로그인 → 채용공고 목록/필터/상세 조회 흐름
  - 캘린더 일정 등록 UI 플로우, 9단계 스타일 개선 이후 확정한 기준선 대비 스크린샷 비교(라이트/다크 모드) — 알림 자체는 OS 레벨이라 Playwright 대상에서 제외하고 메인 프로세스 트리거 함수 호출을 별도 훅으로 검증
  - PDF 업로드 → 첨삭 결과 비교뷰 렌더링 확인
  - CS 문제 등록 → 공개 전환 → 다른 계정에서 공개 문제뱅크 조회까지 UI 플로우(권한 분리 자체는 앞의 RLS 단위 테스트가 담당)
  - 시드 픽스처 기반으로 신규 크롤링 소스(캐치/자소설닷컴) 데이터가 목록 화면에 정상 노출되는지 확인(외부 사이트 실호출에는 의존하지 않음)
  - 패키징된 실행 파일 기동까지 포함해 회귀 방지를 위해 CI에 Playwright 스모크 테스트로 등록
